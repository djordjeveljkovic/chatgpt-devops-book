# Chapter 27 — Firewalls and Network Policy

## Why this matters

A new DispatchDesk deployment listens on TCP 443, but users cannot reach it. The process is healthy and the route points to the correct host. A host firewall, a provider security group or an upstream network policy may still drop the traffic. A firewall rule must match the intended path and protocol at the layer that enforces it.

This chapter examines packet filtering on Linux and the operational change process that protects remote access. It builds on the route, connection and SSH chapters. Read [Chapter 26](026-ssh-and-remote-administration.md) before changing a firewall on a remote host: the management session can use the path the new rule removes.

## Stateful filtering and rule ordering

A firewall applies policy to traffic at a particular boundary. Linux host rules can inspect incoming, outgoing and forwarded packets. A cloud security group, subnet ACL, VPN policy and host firewall each enforce separate controls. Permitting a port at one layer does not override a denial at another. Draw the request and return path, then identify every enforcement point.

A stateful firewall tracks connection flows and can permit return packets that belong to an allowed connection. The initiating request still needs a matching rule. Stateless ACLs may require explicit return traffic rules and can behave differently for ephemeral ports. Stateful tracking uses kernel resources and timeouts; stale or excessive flow entries can themselves affect traffic.

Rules match fields such as address family, source/destination prefix, protocol, port, interface, connection state and direction. Order and base-chain priority determine which rules run. Some rule sets stop at the first verdict; others continue through later hooks or chains. Inspect the actual rules and backend rather than assuming that two firewall managers interpret rule order identically.

A default-deny inbound policy can reduce exposed listeners, but the necessary management and service paths must remain reachable. Outbound policy matters too: DNS, package repositories, databases, telemetry and notification providers require specific egress paths. Avoid an unreviewed `allow all` rule as a debugging shortcut; it can erase the evidence needed to identify the missing dependency.

## nftables, ufw and firewalld

`nftables` is the Linux packet-filtering framework and `nft` is its command-line utility. Read the current kernel rules with sufficient privilege:

```bash
sudo nft list ruleset
```

The output can reveal rules generated by another manager. Do not edit those live rules directly while UFW or firewalld owns the host policy. A manager can replace its ruleset during reload, leaving a manual change lost or creating an unexpected combined policy. `nft list ruleset` is an inspection command; configuration should be changed through the host's chosen manager and reviewed for the precise OS release. [nftables documentation](https://wiki.netfilter.org/wiki-nftables/index.php/Main_Page).

On Ubuntu, UFW provides a higher-level host interface. Inspect before changing it:

```bash
sudo ufw status verbose
sudo ufw show added
```

`status` reports whether UFW is active and its user rules; `show added` lists rules entered through UFW, but neither command displays every other enforcement layer. The same concepts are not the same configuration syntax. Check Ubuntu's version-specific firewall guide and existing provider rules. [Ubuntu Server firewall guide](https://ubuntu.com/server/docs/how-to/security/firewalls/).

On Fedora and RHEL, firewalld commonly manages zones and services. A zone associates policy with an interface or source; inspect the active binding and runtime rules before changing it:

```bash
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=public --list-all
sudo firewall-cmd --permanent --zone=public --list-all
```

The `public` zone is only an example. Confirm the interface's actual zone first, and do not assume that a service name maps to the same port in every installed definition. firewalld separates runtime state from permanent configuration. A runtime change takes effect immediately and may disappear at reload; permanent state takes effect after reload/restart. Verify runtime behavior first, then persist the intended change. [firewalld runtime/permanent guide](https://firewalld.org/documentation/configuration/runtime-versus-permanent.html).

Package tools are `ufw`, `nftables` and `firewalld` on Ubuntu; Fedora and RHEL use firewalld/nftables tooling according to release and policy. RHEL package availability depends on enabled repositories and subscription. Do not enable two managers to control the same host concurrently without a deliberate integration design. Container engines may add their own forwarding rules and alter which interface sees published traffic; revisit the container-specific chapters before attributing that path solely to the host manager.

## Change access without losing SSH

Before a remote firewall change, save the current policy, confirm an out-of-band console works, identify the source address or management CIDR of the current SSH session, and arrange a second authenticated session. Confirm the SSH port and the effective zone/rule source. Prepare a narrowly scoped rollback command and a timed recovery method approved for that system. Keep the existing session open while testing a new one.

For Ubuntu with UFW, the following example adds a rule for SSH from the fictional management subnet `10.20.30.0/24`. Replace it with the approved source range before running. The command changes firewall state and requires administrative privileges:

```bash
sudo ufw allow from 10.20.30.0/24 to any port 22 proto tcp
sudo ufw status numbered
```

Test a new SSH connection from a machine in that subnet before removing any broader rule. If the new rule is wrong, delete the exact new rule shown by `status numbered`, checking its current number immediately before deletion because rule numbers can change:

```bash
sudo ufw delete NUMBER
```

`NUMBER` is a placeholder, not literal input. Avoid enabling UFW remotely until you have verified its default policies and the SSH allowance it will apply. On an already active production host, an unintended default-deny or wrong source range can cut off operations.

For a Fedora/RHEL host using firewalld, first determine the active zone and whether SSH is already permitted. `--add-service=ssh` permits SSH for traffic matching the zone; it is broader than the UFW example's source-scoped rule. Prefer a reviewed source-scoped rich rule when only a management CIDR should connect. If the service-level example is appropriate for a disposable host, record whether SSH was already enabled before changing anything. Run this setup in one shell and keep it open through the independent connection test:

```bash
zone=public
if sudo firewall-cmd --zone="$zone" --query-service=ssh; then
  ssh_was_allowed=yes
  printf '%s\n' 'SSH was already allowed; this test will preserve that rule.'
else
  ssh_was_allowed=no
  sudo firewall-cmd --zone="$zone" --add-service=ssh
fi
sudo firewall-cmd --zone="$zone" --query-service=ssh
```

Do not run cleanup until an independent SSH session from the approved management path succeeds. In the same shell, remove the allowance only if this test observed it was initially absent; do not remove policy another operator or service may have added in the meantime. Recheck the rule and current change ownership immediately before cleanup:

```bash
if [ "$ssh_was_allowed" = no ]; then
  sudo firewall-cmd --zone="$zone" --query-service=ssh
  sudo firewall-cmd --zone="$zone" --remove-service=ssh
fi
sudo firewall-cmd --zone="$zone" --list-services
```

This runtime-only example does not modify permanent policy. If the intended policy is to be permanent, apply the matching `--permanent` change only after runtime behavior and rollback are verified. Runtime and permanent calls are separate. A reload replaces runtime configuration with permanent configuration, so an unpersisted allowance can disappear. `--complete-reload` can terminate active connections and is not routine rollback.

These are host-firewall examples, not complete provider policies. A security group or organizational ACL may also need a reviewed source-scoped allowance. Confirm the actual client source as seen at each layer; VPN, NAT and proxy boundaries can change it. Do not open SSH to the whole Internet merely because an example elsewhere uses port 22.

## Diagnose a denied connection

Harbor can establish SSH to its host, but users cannot establish HTTPS. Confirm the application listens on the expected address and port, then inspect the host firewall's active policy. Check the provider firewall or security group, subnet ACL, load balancer and any source NAT path. The failed TCP exchange from [Chapter 22](022-tcp-udp-and-connections.md) may appear as a timeout when a layer silently drops packets or a refusal when a reachable layer rejects them; these observations narrow the path but do not name the responsible policy by themselves.

Use an authorized client to test the specific destination and port, and capture only the relevant traffic at an approved observation point. Compare source and destination addresses before and after NAT. Firewall logging can expose traffic details and generate volume; enable narrowly and temporarily, then disable or rate-limit it after diagnosis. Do not flush counters or reload rules before recording them.

If traffic reaches the host and the firewall accepts it, return to listener binding, routing and application evidence. If the host emits a reply that never reaches the client, inspect return routing and upstream stateful rules. Repair the missing narrow allowance at the layer that denied the packet, then verify from the original client path and confirm unrelated ports remain blocked.

## Exercises, review questions and takeaways

1. Inspect the active firewalld zone and compare runtime with permanent policy. Guidance: identify a change that would disappear on reload before persisting anything.
2. Plan an SSH firewall adjustment for a remote host. Guidance: name the source range, second-session test, console recovery path, rollback and the rule owner.
3. A TCP connection times out even though the host listener is active. Guidance: examine each provider and host boundary along both paths before widening policy.
4. Explain why a manual nft rule can disappear after a firewalld reload. Guidance: identify which component owns and reconstructs the kernel ruleset.

Review questions: What does stateful filtering remember? Which layer made the observed decision? Why are runtime and permanent rules separate? A strong answer traces direction, source, destination, protocol, manager and rollback evidence.

Change one narrowly scoped rule, test it from the intended path, and preserve a way to restore access. Continue to [Chapter 28](028-nat-proxies-and-connection-tracking.md) to follow how address translation changes that path.
