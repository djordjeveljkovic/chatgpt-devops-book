# Chapter 121 — CI Architecture and Trust Boundaries

## Events, workers and pipeline graphs

A continuous integration platform receives repository events, decides which workflows are eligible, creates a job graph, assigns workers, transfers source and artifacts, injects permitted credentials, collects status and logs, then reports results to developers. A pipeline file is executable automation: repository authors may control shell commands, build tools, test code, dependencies and sometimes the workflow definition itself. A CI design therefore begins with the trust of the event and the code it executes, not with the number of YAML jobs.

Model a pipeline as a graph with explicit edges. A pull request may run formatting, unit tests and static analysis. A protected-branch pipeline may package a release candidate and attest to its source. A separately authorized deployment job may promote the exact artifact digest after checks and approval. Each edge transfers a specific input: a commit, build output, test report, artifact digest, approval or identity token. Avoid implicit connections through a shared workspace, mutable tag, cache or globally scoped environment variable. Record which event can start each stage, which code revision provides the workflow definition, what the stage can access, and who can approve its outputs.

The event source shapes trust. A push to a protected branch typically comes from an authorized repository member; a pull request from a fork can contain arbitrary source code and build instructions. A scheduled or manually dispatched workflow can run a different revision than expected if branch and ref inputs are not constrained. A comment-triggered job may combine an untrusted comment with a privileged token. Treat merge-request code, downloaded artifacts, package scripts and test fixtures as executable input whenever a worker may run them.

GitHub Actions illustrates the distinction between fork-safe pull request workflows and privileged triggers. For fork pull requests, GitHub generally withholds repository secrets and grants a read-only `GITHUB_TOKEN`, subject to repository and organization settings. `pull_request_target` runs with the base repository's trusted workflow and credentials; checking out and executing fork code in that context can expose secrets or write access. Use that event for narrow metadata actions such as labeling when needed, and do not build or run untrusted pull request code with its privileged context. Treat artifacts from an untrusted workflow as untrusted when a later privileged workflow consumes them. Verify current repository policies and event semantics in GitHub's [event reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) and [secure `pull_request_target` guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

GitLab merge-request pipelines can run in a fork project or, when an authorized parent-project member starts them, in the parent project using the fork's CI configuration and the parent project's resources and variables. This is a trust transition: a trusted runner does not make the submitted script trusted. GitLab documents that fork merge-request pipelines cannot access protected variables or protected runners; access for same-project merge requests depends on branch protection, triggering permissions and project settings. Review who may start a parent-context fork pipeline, which non-protected resources and variables it can use, and which runner receives the job. See GitLab's [merge request pipeline](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/) and [protected resource guidance](https://docs.gitlab.com/ci/pipelines/).

Jenkins has a controller that orchestrates work and agents that run build steps. Pipeline definitions and repository build files influence commands executed on agents. The controller should not execute ordinary builds on its built-in node; agents should be isolated according to the code they run and the credentials they can access. In multibranch and organization-folder jobs, SCM scan credentials and item-level credentials may be available to child pipelines; authors who can change a Jenkinsfile may be able to use credentials available to that job. Keep credential scope narrow and separate trusted and untrusted jobs or folders. Jenkins documents [controller isolation](https://www.jenkins.io/doc/book/security/controller-isolation/), [credentials](https://www.jenkins.io/doc/book/security/credentials/) and [multibranch credential risks](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/).

These provider mechanisms are not identical, but the architectural question is the same: which actor controls the code and workflow that runs with a given identity on a given worker? A platform default may reduce exposure without eliminating it. Repository settings, runner configuration, workflow triggers, plugins, branch protections, organization policy and human approvals all affect the effective boundary. Document the deployed configuration rather than relying on a product's general reputation or one checkbox.

## Untrusted code and credential exposure

Any code executed by a job can usually read files and environment values available to that process, invoke network clients, alter the workspace and emit data through logs or artifacts. Masking a secret in console output protects against some accidental disclosure; it does not stop malicious code from encoding or transmitting the value. A job that downloads dependencies or executes package lifecycle scripts can also run code maintained outside the repository. Therefore, separate untrusted validation from privileged release and deployment work.

For untrusted pull requests, grant no deployment credentials, cloud roles, signing keys or write tokens. Use workers with restricted network access and no route to production control planes or internal services. Prefer ephemeral workers with a clean environment for each job; destroy disks, credentials and containers after completion. If workers are reused, prove that workspaces, caches, processes, sockets and credentials cannot cross between trust levels. Self-hosted runners need particular care because a pull request can probe attached networks, filesystem paths, metadata services, local container sockets and previously persisted state. Keep privileged workloads off the same runner pool unless the isolation boundary is deliberately designed and tested.

Scope every token to the job and operation that needs it. In GitHub Actions, declare the smallest `GITHUB_TOKEN` permissions and consider short-lived OIDC federation for cloud access. OIDC reduces the need to store long-lived cloud keys in repository settings, but a workflow that can request an accepted identity token can still obtain cloud access. Restrict the cloud trust policy by repository, branch, environment, audience and other supported claims, and require approval for production environments where appropriate. In GitLab, use protected and environment-scoped variables, protected runners and short-lived identity federation where configured. In Jenkins, define credentials at the lowest applicable folder or item scope and do not bind them around commands that execute contributor-controlled scripts. Each platform has different syntax and controls; test effective identity and denied access in the target service.

Separate build permission from deployment permission. A build worker should produce a candidate artifact without production access. A deployment identity should retrieve an approved artifact by immutable digest, verify its provenance and deploy only to its authorized environment. Require protected-branch or tag policy, reviewers and any required change approval before the privileged stage. A pipeline condition is useful defense in depth, but repository owners who can change the pipeline may alter that condition; protect workflow files and policy outside the authority of untrusted contributors where the platform allows it.

Caches and artifacts also cross trust boundaries. A cache can contain executable binaries, compiler outputs or package-manager state. Do not let untrusted jobs write a cache later consumed by a privileged release without validation and a trust-separated key. Artifacts from fork or merge-request workflows can contain scripts, symlinks, archives, metadata or content crafted to attack the consumer. Validate the archive structure and expected files, bind the artifact to its source commit and producer run, and avoid executing it in a higher-trust job before verification. Do not pass secrets or privileged environment files as artifacts.

Logs and test reports can carry credentials, source code, internal URLs, personal data or malicious markup. Limit access and retention, redact at the source, and do not treat the platform's masking feature as a complete security boundary. Make deployment and signing events auditable, including the principal, workflow revision, artifact digest, approval and target environment. Rotate or revoke credentials after suspected exposure, then assess artifacts produced while the credential may have been available.

## Designing an artifact-producing pipeline

An artifact-producing pipeline should have a stable identity for its output. Build once from a reviewed commit, assign an immutable version or content digest, record source revision and build environment, and publish to a repository with access controls. Tests and scans should identify that exact artifact. Promotion between development, staging and production should move or reference the same digest rather than rebuilding from a mutable branch or tag. If environment-specific configuration changes the binary or image, record and verify that transformation as a separate artifact step.

Artifact provenance answers which source, workflow, builder and inputs produced an artifact. It is useful only if the consumer has a policy for verifying it and the signing identity is protected. A signature proves a relationship to a key or identity; it does not prove that the source was safe, the build was reproducible, the reviewer was competent or the artifact passed required tests. Require the provenance fields and attestations that matter to the organization's risk, store evidence with the artifact, and fail closed when a privileged deployment cannot verify its required evidence.

For DispatchDesk, a public contribution updates a request parser and its tests. The pull-request job checks out the proposed revision and runs tests on an isolated, disposable worker with no deployment secrets, no production network route and a read-only repository token. It may publish logs and a test report but cannot write a release cache or modify a package registry. After merge to the protected branch, a trusted job builds the container once, scans it, records the commit and image digest, and publishes it to the internal registry. A protected release stage verifies the digest and provenance, obtains short-lived deployment identity after the required approval, then promotes that same image to staging and production. Production credentials never enter the fork workflow, and the deploy stage does not execute scripts from the pull-request artifact.

This design makes failure ownership clearer. If a pull request test fails, the contributor fixes source code. If a build cannot publish, the artifact identity and registry policy can be investigated. If provenance is missing, the release is blocked before deployment. If production deployment fails, the rollback or forward-fix process acts on the exact promoted digest. [Chapter 118](../12-kubernetes-production-engineering/118-helm-and-kustomize.md) covers packaging and deployment configuration; this chapter focuses on the trust and artifact path that delivers it.

## Review the effective boundary

Use a threat-oriented checklist during CI design review. For each event, identify the workflow revision and code revision; whether it can be controlled by a fork, branch author, package maintainer or manual user; which runner labels or agent pools can receive it; which network and filesystem resources it can reach; which secrets and token permissions are present; which caches and artifacts it can read or write; and who can promote the result. Repeat the review after changing runner pools, repository settings, plugins, reusable workflows, cloud trust, protected branch rules or artifact retention.

Test the negative cases. An untrusted pull request should not access deployment variables, protected runners, signing identities or writable release registries. It should not be able to poison caches consumed by a privileged build, impersonate a trusted artifact producer, or reach the controller or production network from its runner. A release job should fail if the artifact digest differs from the tested one, provenance is missing, the approval is absent or the target environment is outside its authorization. Audit logs and job records should make these outcomes observable.

Avoid placing secrets into command arguments, generated source files, caches or artifacts. Do not print environment dumps in troubleshooting logs. Protect workflow definitions and deployment policy with code review and ownership rules; if one repository branch can change both untrusted code and the rule that grants production credentials, that rule is not an independent control. Prefer platform-level policy or a protected reusable workflow where supported, while still reviewing who may change that policy. Limit third-party actions and plugins by source and version, pin or verify dependencies under an appropriate update process, and track their permissions and maintenance owner.

## Takeaways

Keep event trust, execution trust and release authority explicit. Isolate untrusted code, grant only the credentials needed by one stage, and promote one verified artifact by digest.

## Exercises and answer guidance

1. A fork pull-request workflow has no explicit secret reference. Can its code still be considered harmless? No. It can execute arbitrary commands, read workspace data, access the network and affect caches or artifacts. Remove unnecessary privileges and isolate the worker.
2. A GitHub workflow uses `pull_request_target`, checks out the fork's head and runs tests. What is the trust error? Untrusted code is executed with a privileged base-repository context that can include secrets and a write-capable token.
3. A GitLab fork merge request runs in the parent project on a trusted runner. Does that make it safe? No. The fork controls CI configuration and code; a parent-context run can use parent resources and variables depending on permissions and settings.
4. A Jenkins multibranch job exposes an SCM credential to a Pipeline. What must be reviewed? Who can edit the Jenkinsfile, which child jobs receive the credential, what it can access, whether untrusted scripts run while it is bound and how the agent is isolated.
5. Staging and production jobs rebuild the same branch independently. Why is this weaker than digest promotion? The binaries may differ because source, dependencies, base images or build environments changed; promote and verify the exact artifact tested in earlier stages.
6. A provenance signature is valid. Does this alone prove the artifact is trustworthy? No. Verify the signer identity and build policy, source revision, dependencies, test evidence and whether the producer itself was trusted.

Review questions: which pipeline inputs are attacker-controlled, where should untrusted validation run, how do artifacts and caches carry trust, and what evidence should a privileged deployment verify?
