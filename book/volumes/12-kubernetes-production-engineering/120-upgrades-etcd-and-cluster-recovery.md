# Chapter 120 — Upgrades, etcd and Cluster Recovery

## Upgrade the platform as a compatibility change

A Kubernetes upgrade changes the API server and often the scheduler, controller manager, kubelet, proxy, CNI, CSI, admission components and provider integrations. A healthy control plane before the change does not prove that workloads, custom resources, webhooks or storage integrations remain compatible afterward. Treat an upgrade as a production change with an inventory, compatibility review, recovery point, staged rollout and measurable exit criteria. The supported procedure differs between managed services, kubeadm clusters and provider-specific distributions; follow the selected service's current runbook.

Start by confirming the current control-plane and node versions, supported target path, release notes and version-skew policy. Kubernetes generally requires minor releases to be upgraded one at a time; do not infer that a supported component skew permits skipping minor control-plane releases. Review deprecated and removed APIs, admission webhooks, CRD stored versions, CNI/CSI compatibility, node images, device plugins, observability and backup tooling. Test rendering and server-side validation against the target version in a representative non-production environment. The official [version skew policy](https://kubernetes.io/releases/version-skew-policy/) and [cluster upgrade guide](https://kubernetes.io/docs/tasks/administer-cluster/cluster-upgrade/) define compatibility limits; provider services may impose additional restrictions.

For kubeadm, the upstream procedure upgrades the primary control plane, additional control-plane nodes and then worker nodes, following the exact release-specific steps. Control-plane nodes are upgraded one at a time, and workers are drained and upgraded in batches that preserve application capacity. A minor kubelet upgrade requires the node to be drained first. kubeadm does not upgrade every CNI or provider integration on behalf of the operator, and it does not reconfigure a cluster as part of the ordinary upgrade. Managed control planes can sequence or expose these steps differently; node pools and add-ons may require separate customer actions. See the current [kubeadm upgrade guide](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/).

Before the change, record control-plane and workload health, available disruption budget, spare capacity, current API usage and the exact deployed versions. Confirm that cluster and application backups meet their separate objectives. Create a canary or maintenance batch, verify API availability and critical workloads after each stage, and stop if readiness, latency, scheduling or error budget crosses the agreed threshold. A node that returns `Ready` is only one signal; verify Pod scheduling, DNS, network policy, storage attach, external routes, workload identity, admission and the actual service request path.

## etcd protects API state, not every workload

etcd is the consistent key-value store Kubernetes uses for API state. Objects such as Deployments, Secrets, ServiceAccounts, RBAC bindings, CRDs and many control-plane records are stored there. etcd availability is essential to API writes and controller progress, though already-running workloads may continue serving traffic during an API outage. etcd is sensitive to disk latency, network delay and resource starvation; quorum loss prevents the cluster from safely committing new state. Operate its membership, certificates, capacity and backups as a critical service, following the topology used by the distribution.

An etcd snapshot protects cluster API state at a point in time. It does not back up application databases, object-store data, external load-balancer configuration, external identity providers, provider account metadata or every file on a node. A cluster recovery plan must combine control-plane state with the application and infrastructure recovery steps required to make workloads usable. Some managed services do not expose customer-operated etcd backups; understand the provider's control-plane recovery contract and preserve application-level backups separately.

Use the backup mechanism documented for the exact etcd and Kubernetes distribution versions. etcd supports a built-in snapshot from a live member; Kubernetes operating guidance also describes supported volume snapshot options for appropriate backing storage. Protect snapshots as sensitive data because they can contain Secrets and other credentials. Encrypt them, restrict access, keep copies in an independent failure domain, record the etcd version and cluster identity, and monitor backup age and completion. A copied data directory is not interchangeable with a verified snapshot procedure. Starting with etcd 3.6, the etcd recovery guide describes using `etcdctl` to create snapshots and `etcdutl` to restore them; earlier releases have different tool guidance. Never apply a restore command from a different etcd release without checking its official documentation.

Snapshot verification and restore testing are distinct. Record the snapshot's integrity check and metadata, but do not treat a successful save or checksum as proof that the cluster can be restored. Restore into an isolated recovery environment using the version-matched procedure, verify API startup and essential objects, confirm encryption keys and external dependencies, and test workload reconstruction. A restored API may contain old node and endpoint information that requires cleanup according to the recovery guide. Test one full restoration path and measure its actual recovery point and time.

## Recovery decisions and sequence

Recovery begins by preserving evidence and deciding which state is authoritative. Determine whether the failure is an API-server outage, a lost control-plane host, an etcd quorum or storage problem, accidental API-object deletion, or application data loss. These failures need different procedures. If etcd quorum still exists, follow the supported member-replacement or repair procedure; do not restore an old snapshot over a functioning cluster just because one member failed. A restore is a disaster-recovery action that creates a new logical cluster state and can discard API changes newer than the snapshot. Coordinate writers and dependent components before using it.

When a complete etcd restore is necessary, follow the exact etcd-version procedure to restore into a clean data directory and form the intended member set, then configure the API servers and clients for that recovered cluster. A restore from an older snapshot can move the etcd revision backwards. Kubernetes controllers and operators maintain informer caches and watches based on revisions; if clients continue from stale watch state, they may not promptly reflect the restored objects. Current etcd recovery guidance for Kubernetes recommends a restore-time revision bump, with the bumped revisions marked compacted, so existing watches terminate and clients relist the restored state. The bump must exceed the revision growth since the snapshot; calculate it from the backup age and write rate using the exact etcd-version runbook. The relevant restore options are commonly named `--bump-revision` and `--mark-compacted`, but do not copy an amount or invocation without confirming support and procedure for the installed etcd release. Do not mix old member data directories with restored data or reconnect stale members without following the documented procedure. Control-plane certificates, encryption-at-rest keys, static Pod manifests, network endpoints, DNS, cloud integration and load balancers may need separate restoration or reconfiguration. Validate API reads and writes, controller progress, node registration and core add-ons before admitting application traffic.

Application recovery follows its own consistency contract. Restore databases and files from application-consistent backups or vendor procedures, not from etcd. The API objects that describe a PVC or StatefulSet cannot reconstruct the backing volume contents. Verify credentials, encryption keys, storage topology and DNS dependencies, then check application-level invariants before routing users. [Chapter 114](114-csi-and-production-storage.md) covers CSI snapshots and storage restore; [Chapter 186](../19-site-reliability-and-recovery/186-backup-engineering.md) covers workload backup engineering. A cluster can have a healthy API and still have unrecoverable business data; the reverse can also be true if a database backup exists but the control plane cannot recreate required services.

DispatchDesk's platform team upgrades a kubeadm cluster and encounters an etcd failure before the maintenance is complete. One control-plane member is unavailable, but the remaining etcd members still have quorum. The operator first freezes additional upgrade actions, checks the distribution's health indicators and approved runbook, confirms which control-plane components and member are affected, and preserves logs and current backups. Because quorum remains, the team follows its member recovery procedure rather than restoring an older cluster snapshot. After the control plane is stable, it resumes the version-matched upgrade one node at a time and verifies workloads and external paths after each stage. A separate exercise later restores an etcd snapshot and the application's database backup into an isolated environment, confirming their independent recovery procedures.

An incident commander should coordinate the restore decision, application owners, storage and identity teams, provider support and communications. Establish a recovery timeline: select the last verified snapshot, identify changes after its timestamp, protect any newer surviving application data, restore the control plane or service, recover workloads and validate user-visible behavior. Record what state may be lost before proceeding. Never claim a recovery point based only on a backup schedule; confirm the actual snapshot time and application consistency.

## Readiness checks and rehearsal

Before maintenance, inspect version and health evidence through the authorized path for the cluster type. For a kubeadm cluster, the upstream guide uses commands and host package steps that are version- and distribution-specific; execute those only under its runbook. General API-level reads can establish a baseline:

```bash
kubectl --context kind-dispatchdesk version
kubectl --context kind-dispatchdesk get nodes -o wide
kubectl --context kind-dispatchdesk get pods --all-namespaces
kubectl --context kind-dispatchdesk get pdb --all-namespaces
kubectl --context kind-dispatchdesk get events --all-namespaces --sort-by=.lastTimestamp
```

The context is illustrative; verify its API endpoint and account before use. These reads do not inspect etcd health, provider maintenance status, CNI/CSI compatibility, API deprecations, backup restore, admission behavior or user traffic. Node readiness and Pod phase are necessary signals but not recovery proof. For cluster-specific etcd health and snapshots, use the restricted administrative procedure documented for that distribution; do not expose peer URLs, client certificates, credentials or snapshot contents in shared logs.

Maintain separate runbooks for routine upgrade, control-plane host loss, etcd member loss, quorum loss, accidental API-state deletion and application-data recovery. Each runbook should define prerequisites, named decision owner, source of truth, tested commands for the exact release, access controls, stop conditions, expected evidence, communication and rollback or forward-recovery criteria. Store backups away from the cluster and ensure on-call staff can access keys during a regional outage. Rehearse through a timed restore, not just a tabletop reading. Update the runbook after every version change and after provider or storage architecture changes.

After an upgrade, compare actual versions and API behavior with the approved target, check admission and controller logs, validate critical add-ons and execute application smoke tests. After recovery, reconcile stale resources carefully, verify that backups are still being created, and document data loss, recovery time and remaining risk. Do not use a version rollback as a general substitute for recovery: API storage conversions, CRD versions, node state and application migrations may not be reversible. Prefer a tested forward fix or restore decision based on the precise failed layer.

## Exercises and answer guidance

1. An etcd member has failed but the remaining members retain quorum. Should the team restore yesterday's snapshot immediately? No. Follow the supported member-replacement procedure while quorum exists; snapshot restoration can discard newer API state and is reserved for the appropriate disaster scenario.
2. A verified etcd snapshot exists, but the database backup is six days old. What recovery point can be claimed for application data? At most the database backup's actual consistent point, subject to its restore test; etcd state does not recover database contents.
3. The team wants to skip one Kubernetes minor release because component skew permits older kubelets. Is that sufficient? No. Upgrade path rules and tool/provider support can separately prohibit skipping a minor control-plane version; use the release- and distribution-specific upgrade guide.
4. All nodes become Ready after an upgrade. Is service recovery complete? No. Verify controllers, add-ons, scheduling, storage, DNS, identity, external routes and user-facing SLOs.
5. A restore would rewind API state but external data has continued changing. What must the incident commander coordinate? Freeze or reconcile writers, identify which state is authoritative, quantify what snapshot-time data may be lost, and validate application-level backups and external dependencies before restoration.

Review questions: what does etcd protect, why are cluster and application backups separate, how do quorum repair and snapshot restore differ, and what evidence defines a successful upgrade or recovery?
